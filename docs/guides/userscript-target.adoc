= Shipping a userscript with AffineScript
:toc: macro
:toclevels: 3

toc::[]

A *userscript* is one JavaScript file, loaded into somebody else's page by a
manager (Tampermonkey, Greasemonkey, Violentmonkey, Userscripts/Safari). The
manager injects it as a classic script: no module loader, no bundler, no
build step on the user's machine, and a metadata block that decides which host
capabilities (`@grant`) the script may touch. The `userscript` target emits
exactly that artefact from an AffineScript module — one ES2020 IIFE, plus an
optional `// ==UserScript==` banner.

[source,bash]
----
affinescript compile src/probe.affine --target userscript -o probe.user.js
affinescript compile src/probe.affine --iife            -o probe.user.js   # same build
affinescript compile src/probe.affine --target userscript \
    --banner src/probe.meta.js -o probe.user.js
----

`userscript` and `iife` are reserved words for `--target`; every other
`--target` value is still an LLVM triple (see `affinescript compile --help`).
The default output name for this target is `out.user.js`.

== The single-file contract

The emitted file is one capsulated IIFE in strict mode:

[source,javascript]
----
// Generated by AffineScript compiler (userscript target).
// SPDX-License-Identifier: MPL-2.0
(function () {
  "use strict";
  // ---- AffineScript userscript runtime
  // ... only the runtime sections the program reaches ...
  // ... your functions ...
  try {
    const __as_result = main();
    if (__as_result && typeof __as_result.then === "function") {
      __as_result.catch((e) => console.error("[affinescript] main failed", e));
    }
  } catch (e) {
    console.error("[affinescript] main failed", e);
  }
})();
----

What the artefact never contains — all four are checked on every build, not
just documented:

[cols="1,3"]
|===
|Absent |Why

|`import` / `export` |A userscript is not a module; a manager injects a
classic script, and `export` outside a module is a syntax error.

|`import(...)` (dynamic import) |Async module loading from a page-injected
script is blocked by page CSP and by manager sandboxing.

|`eval` / `new Function` |Requires `unsafe-eval` in the page CSP, which a
userscript cannot grant itself.

|top-level `await` |Only legal in modules. An `async` `main` is *observed*
(the returned promise is caught) rather than awaited.
|===

The runtime is emitted section by section: a script that never touches
`GM_*` storage never carries the storage helpers, and a script with no DOM
calls carries no DOM helpers.

== `--banner FILE`: the metadata block

`--banner FILE` prepends `FILE` verbatim, so the block is complete and yours
to own:

[source,javascript]
----
// ==UserScript==
// @name        AffineScript userscript fixture
// @namespace   https://affinescript.dev/e2e/userscript
// @version     1.0.0
// @match       https://affinescript.test/probe
// @grant       none
// ==/UserScript==
----

The file must be a complete metadata block: a `// ==UserScript==` opener, a
`// ==/UserScript==` closer, and the opener first. A banner that does not open,
never closes, or closes before it opens is refused (exit non-zero, `E0827`
with `--json`) — a half-parsed metadata block would silently ship a script
that a manager treats as ungranted. Nothing inside the block is rewritten:
`@grant`, `@match`, `@run-at` reach the manager exactly as written.

== `stdlib/Userscript.affine`: the host surface

A userscript runs in a page it does not control, so *whether a capability
exists* is a runtime question. The stdlib turns that into data and typed
errors instead of `typeof`-sniffing sprinkled through the program.

[source,affine]
----
use Userscript::{
  Node, MenuCommand, body, element, set_attribute, set_text, append, remove,
  capabilities, describe_error, get_setting, set_setting, storage_backend,
  register_menu_command, release_menu_command, listen_window_once
};

pub fn main() -> Unit {
  let host = body();
  let box = element("div");
  set_attribute(box, "id", "affinescript-userscript-probe");
  set_text(box, "AffineScript userscript is running");
  append(host, box);

  match set_setting("affinescript-userscript-probe", "42") {
    Ok(_) => println("setting-written"),
    Err(e) => println("setting-write-failed=" ++ describe_error(e))
  };

  match register_menu_command("Probe", fn() => println("clicked")) {
    Ok(command) => { /* ... release it on teardown ... */ },
    Err(e) => println("menu-unavailable=" ++ describe_error(e))
  }
}
----

=== Capabilities

`capabilities()` reports what this page's manager exposes
(`manager`, `gm_storage`, `local_storage`, `menu`, `style`, `notification`),
and `storage_backend()` names the backend a setting will actually use:
`"manager"`, `"localStorage"` or `"none"`. Every stdlib operation consults it
first, so the same compiled file behaves correctly under `@grant none` and
under a full grant list — which is why the fixture is compiled once and run
three ways (see <<_testing_this_target>>).

=== Typed errors, never swallowed

Every operation returns `Result<_, UserscriptError>`:

[cols="1,3"]
|===
|Case |Meaning

|`ManagerMissing(String)` |The manager grants no such capability (checked with
`GM_*` feature detection, never assumed).

|`HostRejected(String)` |Granted, but the host call itself failed. Carries the
host's message.

|`StorageDenied(String)` |`localStorage` exists but the page refuses access
(opaque origin, private-mode quota 0).

|`InvalidKey(String)` |The setting key is empty, longer than 128 characters, or
contains a control character — rejected before the host is touched.
|===

`describe_error` renders one for a log line. Nothing throws out of the
capsule: `main` is wrapped, so an unexpected host error becomes a
`console.error("[affinescript] main failed", e)` line instead of a broken page.

=== Settings: manager first, `localStorage` second

`get_setting` / `set_setting` / `delete_setting` prefer `GM_getValue` /
`GM_setValue` / `GM_deleteValue` and fall back to `localStorage`, so a script
still remembers things under `@grant none`. `Ok(None)` means "not set" and is
never conflated with `""` or with an error. Structured manager values come
back as their JSON text.

=== Affine handles

Everything that outlives a statement — a menu command, an injected style, a
notification, an event listener, a timer — arrives as a handle and leaves
through its release function:

[source,affine]
----
pub fn inject(css: String) -> Unit {
  match add_style(css) {
    Ok(sheet) => {
      @linear let style = sheet;   // exactly one release, proven statically
      match release_style(style) {
        Ok(_) => println("style released"),
        Err(e) => println(describe_error(e))
      }
    },
    Err(e) => println("style-unavailable=" ++ describe_error(e))
  }
}
----

Bind the handle `@linear` and the quantity checker (`lib/quantity.ml`) proves
the release statically: a dropped handle and a double release are both
compile errors. `test/e2e/userscript/negatives/handle_leak.affine` is the
planted negative control.

A one-shot page event is the case where a handle would be circular (the
handler would have to release the listener it is part of). `listen_window_once`
and `listen_element_once` exist for it: the emitted runtime removes the
listener *before* running the handler, so there is nothing to release and no
leak.

=== DOM surface

`body`, `element`, `text_node`, `query` (→ `Option<Node>`),
`append`, `remove`, `set_attribute`, `remove_attribute`, `set_text`,
`add_class`, `remove_class`. `Node` is opaque in AffineScript; at runtime it
is an ordinary DOM node, or `null` when the page has no document. The helpers
return `null` instead of throwing, so a script that runs on the wrong page
degrades quietly instead of blowing up.

== What is refused at build time

The target is deliberately narrower than the other JS backends: anything it
cannot express in one non-module file is a *build* error naming the construct
and the module, never an optimistic same-named JS call that would throw in the
page, in front of a user.

[cols="1,3"]
|===
|Refused |Reason

|`extern fn` without a userscript binding |The host surface is a closed
allowlist (the `us_*`, `gm_*` and `dom_*` functions declared in
`stdlib/Userscript.affine`). Diagnostic:
``userscript target: unsupported `extern fn us_not_a_capability` (no
userscript binding) (in module …)``.

|Effect handlers (`handle`/`resume`) |No lowering outside the WASM backends;
the runtime is a plain JS IIFE with no continuation machinery.

|`unsafe` blocks |There is no linear memory to point at.

|Float-cell records |No cell lowering in this target.

|`--wasm-gc` |The target emits one JS file and no module; combining the two is
refused rather than silently ignored.
|===

All of these report `E0827` under `--json`.

== Reachability, not minification

`use prelude::*` and a broad `use Userscript::{...}` are fine: the target
prunes to what `main` reaches. Unreachable top-level functions and the runtime
sections only they used disappear; constants, types, impls and externs are
always kept (they are declarations, not code). Nothing is renamed, folded, or
inlined — this is reachability, and `test/e2e/userscript/reachability.affine`
pins both halves of it (live path present, dead helper and unused manager
section absent).

== WASM delivery: not used, and why

The userscript target emits *pure JavaScript*. No WASM module, no base64
payload, no embedder.

* There is nothing to put in a module. The target's lowerings are DOM
  operations, event listeners, storage and timers — none needs linear memory,
  and the constructs that would (handles, `resume`, `unsafe`) are refused at
  build time rather than miscompiled.
* Page CSP is not negotiable. `WebAssembly.instantiate` needs
  `wasm-unsafe-eval` in the page's `script-src`. A userscript runs in the
  *page's* CSP context; a manager's sandbox does not lift it. A base64 module
  would therefore work on some pages and fail on the rest — as a load-time
  failure in somebody else's page.
* Size. The pure-JS artefact for the CI fixture is 18,325 bytes (the
  hello-DOM script is 4,142 bytes, the reachability script 4,153 bytes). The
  same program as a module would add a base64 payload (≈ +33% on the module)
  plus a loader and a JS fallback path, and the fallback would have to be
  maintained anyway.

*If* a future program genuinely needs numeric throughput that JS cannot give,
the recipe is the ordinary web one, and it stays outside this target: ship the
module as an `@resource`, guard `typeof WebAssembly === "object"` plus a
`try/catch` around `WebAssembly.instantiate`, and fall back to the pure-JS
build when the page blocks it. Nothing in the target or the stdlib assumes
WASM, so that fallback is the artefact this compiler already produces.

== The ESM DOM runtime (`packages/affine-js`) does not bundle to an IIFE

`packages/affine-js` is the JS interop layer for **WASM** modules (loader,
marshalling, `sandbox.js`); `affinescript-dom` is its guest-side virtual DOM.
It is published as ESM. An IIFE build of it for userscripts was attempted and
is blocked by the code itself, not by tooling preference:

[source,bash]
----
$ esbuild packages/affine-js/mod.js --bundle --format=iife --global-name=AffineJS
▲ [WARNING] "import.meta" is not available with the "iife" output format
✘ [ERROR] Could not resolve "node:fs/promises"     (packages/affine-js/loader.js:112)
✘ [ERROR] Could not resolve "node:url"             (packages/affine-js/loader.js:113)
----

The loader reads `import.meta.url` for its base path and reaches for
`node:fs/promises` and `node:url` through dynamic `import()`. Neither exists in
a page, and `import.meta` is empty in IIFE output — so an "IIFE build" would
have to be a rewritten loader (new JS, and a semantic change to a published
package), and the emitted dynamic imports would violate the same no-dynamic-
import rule the target enforces. That rewrite is out of scope here.

What a userscript gets instead is the target's own inlined DOM runtime — the
`__as_dom*` helpers in the artefact, which are exactly the operations
`stdlib/Userscript.affine` declares — plus a reconciler authored in
AffineScript: **`stdlib/UserscriptDom.affine`**.

`UserscriptDom` is the IIFE-buildable answer to `affinescript-dom` for this
target: `Spec`/`Element`/`Group` values over opaque `Node` handles, with
`create`, `patch` (attributes added *and* removed, text rewritten only when it
changed), `unmount`, and `Group.reconcile` (patch by position, append the
surplus, remove what the new list no longer reaches). It is a reconciler, not a
vdom diff: an `Element` remembers what it was created with, which is what makes
an in-place patch possible without a vnode tree — the target has no
`get_attribute`, and a recursive vnode type is not expressible.

Because it is ordinary AffineScript, it is compiled by this target into the
same single file as the rest of the script: no loader, no wasm, no byte budget
of its own (only what it reaches is emitted). Keep `affine-js` where a WASM
module is actually being loaded.

== Testing this target

[source,bash]
----
./test/e2e/userscript/run.sh          # or: ./tools/run_userscript_tests.sh
----

The runner compiles `probe.affine`, checks the single-file contract, the
`--target`/`--iife` equivalence, the banner happy path and both refusal cases,
the `--wasm-gc` conflict, both negative controls, and reachability; then runs
the compiled script in a page and asserts the whole lifecycle:

. a `<div>` is appended and carries its text,
. a setting round-trips (manager store under `@grant GM_*`, `localStorage`
  under `@grant none`, typed error on a page that denies storage),
. a menu command registers and is released exactly once,
. an injected style is released,
. teardown removes the `<div>`, and the listener spy shows the one-shot
  listener removed with nothing live afterwards.

Two engines, same assertions: `playwright` (headless Chromium — the CI path,
reusing the pinned install from `affinescript-tea/e2e`) and `jsdom` (a DOM
implementation, for machines that cannot download a browser). With neither
available the runtime half prints a loud `SKIP` and the static and refusal
checks still run; `AFFINESCRIPT_E2E_STRICT=1` (set in CI) turns that skip into
a failure.
